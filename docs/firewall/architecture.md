# Firewall Blocking Architecture

## Control plane vs enforcement plane

The project separates network-data discovery from RouterOS enforcement.

```text
Control plane
Domain / ASN / CIDR input
        ↓
Normalize + validate
        ↓
DNS / CNAME / BGP / registry resolution
        ↓
Canonical network objects
        ↓
RouterOS script generation

Enforcement plane
        ↓
address-list
        ↓
filter rule
        ↓
forward / input / output decision
```

## Choosing the enforcement chain

`forward` handles traffic passing through the router and is the normal location for client-to-internet destination blocking.

`input` handles traffic destined for the router itself. Use it for protecting router services, not for ordinary client destination blocking.

`output` handles traffic generated by the router. It can be relevant to DNS, NTP, update, monitoring, or management restrictions originating from the router.

## Identification methods

### DNS-derived IPs

Good for services whose active endpoints are represented by DNS records, but incomplete when the application uses additional domains, CDNs, anycast, embedded endpoints, or non-DNS control paths.

### ASN/BGP prefixes

Useful for broad infrastructure coverage. It can overblock when a network is shared by multiple services.

### Specific CIDRs

Useful when the service publishes or consistently uses identifiable networks. Requires periodic verification because routing announcements change.

### Layer7 signatures

Useful when IP-based identification is not stable and traffic exposes a reliable application-layer signature. It carries higher CPU cost and protocol limitations.

## Policy hierarchy

A practical generated policy should prefer:

1. explicit, narrow address-list matches
2. verified CIDR coverage
3. ASN-level coverage when the overblocking trade-off is acceptable
4. Layer7 signatures when IP-based enforcement is insufficient

This hierarchy is a design guideline, not a universal rule; the appropriate method depends on the network and objective.

## Verification

Before deployment, verify:

- target addresses are correct
- the rule is in the intended chain
- an earlier accept rule does not bypass it
- IPv4 and IPv6 are both covered where required
- management traffic remains available
- logs are not excessive
- rollback is known
