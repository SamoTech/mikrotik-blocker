# MikroTik Firewall Blocker — Product Vision

## The idea

MikroTik Blocker is evolving from a domain-to-RouterOS script generator into an open-source **Firewall Intelligence Platform for MikroTik RouterOS**.

The core promise is simple:

> **Describe what you want to block. Understand exactly what will happen. Generate a safe RouterOS policy. Keep it updated. Share it with the community.**

The project should become the place MikroTik administrators visit when they need a reliable, explainable, reusable way to turn a security or access-control requirement into RouterOS firewall policy.

## Why this is different

A conventional blocker produces IP addresses or a script. MikroTik Blocker should produce a **policy package**:

- intent: what the administrator wants to block
- evidence: domains, IPs, ASNs, BGP prefixes, DNS records and protocol signals used
- scope: exactly which traffic is affected
- implementation: address-list, raw, filter, DNS, TLS or Layer7 strategy
- compatibility: RouterOS version and feature requirements
- performance: expected CPU / rule-count impact
- safety: collision, shared-infrastructure and false-positive warnings
- deployment: copy, download, API push or scheduled refresh
- rollback: deterministic removal of everything generated by the policy
- provenance: source and verification timestamp for network data

This makes the output auditable instead of being a black-box block script.

## Product pillars

### 1. Firewall Recipe Registry

A curated collection of reusable blocking recipes such as:

- social platforms
- streaming platforms
- gaming platforms
- advertising and tracking
- malware infrastructure
- suspicious DNS resolvers
- cloud providers
- VPN / proxy infrastructure
- country or region CIDR policies
- custom enterprise deny policies

Every recipe should contain machine-readable metadata and a human-readable explanation.

### 2. Firewall Policy Compiler

Convert an intent into a RouterOS policy:

`Intent → Evidence → Resolution → Risk Analysis → Policy → Validation → Deployment`

The compiler should support multiple enforcement strategies rather than assuming that every block should become a simple forward/drop rule.

### 3. Firewall Doctor

Analyze an existing exported RouterOS firewall configuration and report:

- rule-order problems
- ineffective rules
- duplicate address-list entries
- IPv4-only policies where IPv6 bypass is possible
- unsafe broad CIDRs
- expensive Layer7 rules
- missing established/related handling
- missing rollback markers
- conflicting accept/drop policies
- suspicious or unreachable rules

The doctor should explain every finding and provide a corrected RouterOS snippet where possible.

### 4. Policy Simulator

Before deployment, show what a generated policy is expected to affect:

- domains
- IPs and CIDRs
- ASNs
- IPv4 / IPv6 coverage
- TCP/UDP ports
- RouterOS chains
- estimated rule count
- potential shared-hosting collateral

The simulator should clearly distinguish **confirmed**, **inferred**, and **unknown** data.

### 5. Live Intelligence

Network data changes. The platform should treat BGP prefixes, DNS answers and platform ownership as time-sensitive intelligence.

Every generated policy should expose:

- source
- fetched time
- verification time
- expiration / refresh expectation
- confidence
- fallback data used

Static mappings are resilience data, not permanent truth.

### 6. Community-first sharing

Make every recipe easy to share.

A user should be able to share a stable recipe URL or GitHub path that explains:

- what it blocks
- why it works
- what it may accidentally affect
- RouterOS compatibility
- generated commands
- update history
- test status

The repository becomes both the source and the distribution channel.

## Viral loop

The growth mechanism should be product-driven rather than dependent on advertising:

`Useful recipe → Shareable result → GitHub link → RouterOS administrator uses it → stars / contributes → new recipe → more discoverability`

Important share surfaces:

- GitHub README examples
- recipe pages
- copyable RouterOS snippets
- badges showing RouterOS compatibility
- "Generated by MikroTik Blocker" attribution in exported scripts
- changelog entries for network-data changes
- contribution templates for new platforms and recipes

## Golden rule

Do not optimize for the largest block list.

Optimize for **correctness, explainability, reversibility and operational safety**.

A smaller policy that an administrator can understand and trust is more valuable than a huge opaque list.

## North-star metric

The primary product metric should be **successful firewall policies deployed**, not raw resolution count.

Supporting metrics:

- unique recipes used
- generated policies
- validated policies
- repeat users
- community contributions
- recipe stars / forks
- failed or rolled-back deployments
- false-positive reports

## Phased roadmap

### Phase A — Make the repository the reference

- canonical firewall documentation
- recipes catalog
- RouterOS examples
- AI agent context
- CI integrity checks
- source/provenance policy

### Phase B — Make the tool operationally safer

- policy manifests
- deterministic rollback
- dry-run mode
- conflict detection
- IPv4/IPv6 coverage report
- rule-cost estimate
- stronger RouterOS validation

### Phase C — Build the Firewall Doctor

- import RouterOS exports
- parse filter/raw/mangle/NAT/address-list sections
- detect common mistakes
- explain findings
- generate remediation snippets

### Phase D — Build the Recipe Registry

- machine-readable recipes
- categories and tags
- versioned recipes
- test status
- community contribution workflow
- recipe sharing URLs

### Phase E — Automation

- scheduled refresh
- MikroTik API deployment
- webhook-triggered updates
- signed policy manifests
- deployment history
- rollback from the previous known-good policy

### Phase F — Ecosystem

- CLI
- GitHub Action
- REST API
- Terraform-style policy definitions
- integrations for monitoring and notifications
- community-maintained recipe packs

## Positioning

The project should be described consistently as:

**MikroTik Firewall Blocker — open-source firewall intelligence, policy generation and automation for RouterOS.**

Not merely:

- an IP blocker
- a domain resolver
- a script generator
- a web UI

Those are implementation components. The product is the **firewall policy intelligence layer** around RouterOS.
